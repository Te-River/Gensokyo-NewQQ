# Rust 重写 · M0 脚手架

对应设计：`01-architect-design.md` §1（布局）/ §8（里程碑）/ §9（安全与供应链）。
M0 只新建 Rust 工作区与 CI，**不改动任何 Go 代码**。

## 默认裁决（设计 §10 的 5 个开放问题，M0 按下列默认值执行，lead 可随时推翻）

1. **保留 Go 二进制一版用于 bbolt 导出**：M1 的 idmap 迁移走 Go 侧 `legacy-export` 导出 JSONL，Rust 只消费 JSONL；Go 代码在 M4 前不删。
2. **android 目标保留但标记实验性**：`aarch64-linux-android` 仍在构建清单内，CI 失败不阻塞合入，文档注明实验性。
3. **保留全部 action 别名**：以 `callapi.RegisterHandler` 全集为准，含已废弃别名（如 `send_group_msg` → `send_to_group`），别名指向同一 handler 实现。
4. **gRPC 客户端 + 服务端都保留**：`proto/` 的 17 个 RPC 双向实现，字段号不动。
5. **性能基线**：常驻内存 ≤ Go 版 1.2 倍，吞吐不低于同配置 Go 版；M4 以 72h 压测验收。

- YAML：`serde_norway 0.9.42`（`serde_yaml` 的维护分支，RustSec 推荐）；`serde_yml` 因 RUSTSEC-2025-0068（unsound/unmaintained）弃用。

  **与 Go 差异清单**（均已代码注释登记）：
  - 建连失败 warn 降级本地 vs Go panic（Rust「可选能力失败只 warn」口径）
  - gRPC RPC 30s 超时 + 5s 建连上限 vs Go context.Background() 无超时（有意安全性差异）
  - 服务端模式不阻塞主线程（与 HTTP 共存）vs Go 专职进程 grpcServer.Serve 阻塞
  - /getid 按实际状态隐藏（服务端真起或远程真挂）vs Go lotus_grpc=true 一律不挂；降级时保留挂载（仍带 IDMapAuthMiddleware）
  - HTTP 回退不带 token/timestamp（Go buildGetIDURL 是死代码；设 lotus_password 会 401，存量缺陷照抄，修复另立任务）
  - 怪癖照抄：lotus+lotus_grpc 时不查 lotus_without_idmaps（仍走 gRPC 客户端，装配处 warn）
  - 语义微差：delete_config 远程恒 true（Go 只回 error）；store_cache_with_ttl 远程忽略 TTL（Go type=16 无参数）；update_virtual_value_pro 远程单次 RPC（非两次重绑定）
  - 数字解析比 Go float64 中转更精确；超 4MiB 显式报错（Go 靠截断解码失败，同为 Err）
  - backup_port 作用于 Rust 主 listener（正向 WS；Go 是主 HTTP 服务器 port），端口语义映射已注释

  **与 Go 差异清单**（均已代码注释登记）：
  - ① 本地短链 mint 失败照抄 Go 怪癖仍拼悬空 `https://{server_dir}/url/`（`message_parser.go:1784-1789` 无条件拼接，同 HTTP 无 token 缺陷口径，修复另立任务）；lotus 分支保持 Go 语义（失败→空串、成功→远端完整 shortURL）
  - ② `auto_escape` 不设门控（lead 裁决：Go handler 不消费该字段，URL 变换恒由 `transfer_url` 门控）
  - ③ QR PNG 字节级跨库差异（image crate 重采样/压缩 vs go-qrcode 逐像素 floor+BestCompression），parity 目标为矩阵级
  - ④ mint 拼接参数（`server_dir`/`port`/`force_ssl`/`lotus_password`）逐调用现读 live 快照（Go `GenerateShortURL` 每次 `config.GetXxx()` 同口径），boot 只固化「变体选择」；`server_dir`/`lotus`/`lotus_password` 属重启项，改后快照整体冻结（`manager.rs:114-122`），固化变体无可观测差异。残留差异只剩 config 层既有口径一条：Go 重启项变更**自动重启**（`config.go:166-173` `sys.RestartApplication()`）vs Rust 手动重启
  - ⑤ `mint: Option<&UrlMint>`：`None`（短链库未装配）时短链分支**保留 URL 原文不改写**，整次 `transform` 最多一条 `warn`（带 `count`、不含全 URL）——Rust-only 防御路径，Go idmap/db 恒存在无对应态（删空等于静默丢用户内容，比 Go 悬空链接更糟）
  - ⑥ QR 重入 `depth≤1` 硬门（Go 靠 base64 文本天然无 URL 终止，Rust 防御病态 base64 恰含 URL 形态子串）
  - ⑦ Rust workspace 无 small feature（Go `//go:build !small` 的 QR stub 无对应物，QR 恒编译，登记）
  - ⑧ lotus 响应解码比 Go 严：`serde_json::from_str::<HashMap<String,String>>` 不容忍 JSON 尾随垃圾，Go `json.Decoder.Decode` 容忍——仅畸形响应时行为有别（同为 warn + 空串，日志文案不同）
  - ⑨ 长混合字母数字内容两库分段优化器可能选不同 QR 版本（module 数不同）；解码载荷等价为准（rqrr 回读已验，`qr.rs` 金样在模块数不等时只断言语义）
  - ⑩ lotus mint 最坏延迟 = 30s × 同一条消息 URL 数（Go 同口径），且未复用 `boot::shared_transport()`（独立 reqwest 客户端、不共享连接池）——本轮不做该重构，登记为后续项
  - ⑪ `transfer_url`+`url_to_qrimage` 同开时 QR 条与正文条**各推一条** `c2c_wakeup_resp` notice（对齐 Go 每个发送出口都 `sendWakeupNotice`），被动额度占 2；「QR 图已发、正文失败」的残缺窗口存在（子发送失败已升 `warn` 级日志）——运维开启两键时需知悉
  - ⑫ M-B 已闭环（P56-F3）：`LotusMint::try_new` 在构造 client 前预检 `rustls::crypto::CryptoProvider::get_default().is_none()`（`idmap/http_remote.rs` spawn 同款口径）——reqwest 0.13.5 在无进程级 provider 时 `Client::builder().build()` 直接 **panic**（`async_impl/client.rs:2501`）而非返回 `Err`，`Result` 单独兜不住，workspace `panic="abort"` 下嵌入方配 `lotus=true` 会 boot 期终止进程；现 provider 缺失返回 `Err` 并由 `attach_url_mint` 记 `error!` 不注入 mint，**不注入的后果**是短链分支保留 URL 原文（M-C 语义），不崩进程；生产二进制由 `gensokyo-bin` startup 先装 ring，此预检在正常路径不触发。runtime 的 `rustls` 依赖随之从 dev 升入 `[dependencies]`（workspace 定义 default-features=false 无 provider，no-provider 惯例不破）
